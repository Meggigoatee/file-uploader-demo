# 단계별 구현과 TDD 계획

작성일: 2026-10-22 (Asia/Seoul). 상태: **수정 계획 승인 / S0~S6 구현·로컬 회귀, S8 배포·원격 검증 완료**. S7 조건부 옵션은 생략했다. 실제 실행은 TDD_LOG/VALIDATION을 따른다.

이 문서는 구현 전에 작성한 승인 기준이다. 사용자가 수정 계획을 승인한 뒤 S0부터 실제 코드와 테스트를 작성했다. 환경·하네스 스모크를 기능 Red/Green으로 세지 않는다.

## 범위와 근거

- [PLAN](./PLAN.md)의 필수 A1~A4/B1~B3, USER-01/02/03/05/06, AI-01/02/03/05/06/08 범위를 구현한다. API/DB/파일 규칙은 [DESIGN](./DESIGN.md), 판정·실패 기준은 [DECISIONS](./DECISIONS.md), 화면은 [UI_UX](./UI_UX.md)를 따른다.
- 5 MiB/본문 6 MiB/목록 10개, 원문 20자·UTF-8 이름 255바이트, 누적 256 MiB/500회 등은 기존 문서의 설계값이다. 원본 과제의 필수 조건과 구분하며 새로 합의된 기능으로 포장하지 않는다. 변경이 필요하면 근거와 범위 변경을 먼저 기록한다.
- 카테고리 필터·일괄 변경(USER-04a/04b)은 S7의 조건부 옵션이다. 핵심 기능이나 검증·제출보다 먼저 구현하지 않는다.
- 시그니처/악성코드 검사, 상태 조회 API, 자동 재시도, 멱등 키·중복 저장 방지, 파일 보관함/다운로드/미리보기, 로그인, SHA-256·빈도 제한은 현재 구현 범위에 넣지 않는다.
- 설치된 Vue/TypeScript/Vite/Workers/D1/R2/Vitest/Playwright와 PC 전역 pnpm 스토어를 사용한다. 버전 변경·새 라이브러리·프레임워크·범용 계층을 계획에 추가하지 않는다.

아래 순서·테스트 묶음은 사용자 제약에 맞춰 AI가 구성한 실행안이다. 기존 기능 합의와 이번 계획의 사용자 승인은 구분한다.

## 핵심 구현을 이끌 테스트

모든 행은 **작성 예정인 테스트 명세**다. 예상 결과를 실제 Red/Green 실행 결과로 기록하지 않는다. V 번호는 [기존 검증표](./VALIDATION.md)의 추적 ID이며 새 기능 ID가 아니다.

### Cloudflare 장애·한도 응답의 모방은 제외

2026-10-22 사용자 확인 요청에 따라 **실제 Cloudflare 운영 장애·계정 사용량/리소스 한도 초과 응답을 충실하게 모방하는 테스트는 제외**한다. D1/R2 메서드에 임의 Error를 던지거나 503을 만들어 실제 Cloudflare 장애를 검증했다고 하지 않는다. 이전의 포괄적 ‘네트워크/DB/R2 장애·예산 소진’ 표현을 아래처럼 좁힌다.

- **유지 — 앱 자체 예산:** `upload_budget`의 256 MiB/500회 경계는 로컬 D1 행을 상한 근처로 설정하고 실제 조건부 갱신·예약 거절·R2 미호출·앱의 `UPLOAD_QUOTA_EXCEEDED` 응답으로 확인할 수 있다. Cloudflare의 계정 예산·무료량과 다르다.
- **유지 — 제어 가능한 앱/클라이언트 조건:** 실제 DB의 고정 정책 누락, 브라우저 요청 차단, 실제 저장 후 응답 전달 차단, 앱 자체 예산 거절에 대한 화면의 중단/실패 처리. 플랫폼의 실제 장애 응답을 재현한 것으로 분류하지 않는다.
- **제외 — 제공자 장애 재현:** Cloudflare 서비스 장애, D1/R2의 실제 연결·저장 장애/과부하/계정 한도 초과, Workers 실행 중단·에러 페이지의 정확한 코드/본문/타이밍을 인위적으로 재현하는 검사. 이때의 실제 동작은 미검증으로 남긴다.

앱의 일반 오류 처리·실패 시 저장 중단 설계는 유지한다. 제외하는 것은 위 제공자 응답의 모방·검증 약속이며, 앱 오류 응답을 Cloudflare 응답과 동일시하지 않는다. [Workers Limits](https://developers.cloudflare.com/workers/platform/limits/)는 한도별 1027/1102 같은 서로 다른 Cloudflare 오류를 설명하고, [D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/)은 Free 한도 초과 시 쿼리 오류를 설명한다. [R2 Pricing](https://developers.cloudflare.com/r2/pricing/)의 무료 제공량도 앱의 자동 중단 예산과 같은 개념이 아니다.

테스트 격리는 서로 다른 테스트 사이에 적용한다. 동시성 한 사례의 여러 요청은 **같은 DB·예산 행**을 사용한다. T 경계·응답 유실은 테스트 fixture에서 제어하며 임의 sleep·운영용 제어 API·상태 테이블을 추가하지 않는다. 브라우저 요청 abort만으로 서버 저장 완료를 추정하지 않는다.

## 한 번의 TDD 루프

1. **범위 선택:** 단계/TC/V 번호와 바꿀 동작 하나를 고른다. 직전 완료 루프의 회귀 결과를 기존 기준으로 연결한다.
2. **Red:** 테스트를 먼저 작성해 실제 실패를 실행·보존한다. 기대값/실제값, 실패 메시지, 재현 명령과 원인을 [TDD_LOG](./TDD_LOG.md)에 기록한다. import·문법·연결 문제는 환경/테스트 구성 오류로 구분하고 기능 검증의 Red로 대체하지 않는다.
3. **원인 판단:** 미구현·제품 결함·테스트 오류·환경 오류를 구분한다. 테스트의 기대값이 합의/설계와 다른 경우 이유를 기록해 명세와 맞춘다. 통과만을 위해 기대값을 낮추지 않는다.
4. **Green:** 해당 실패를 해결하는 최소 구현을 한 뒤 대상 테스트를 다시 실행한다. 실패하면 같은 루프의 시도 번호를 올려 새 실패 원인과 수정 내용을 기록한다.
5. **Refactor:** 동작을 유지하면서 중복·함수/컴포넌트 책임·이름·불필요한 분기를 정리한다. 일반 Repository/Service·DI·새 기능을 만들지 않는다. 정리할 항목이 없으면 검토 결과와 이유를 기록하고 회귀 확인을 생략하지 않는다.
6. **재검증·회귀:** 리팩토링 뒤 대상 테스트를 포함해 **지금까지 구현된 기능의 전체 단위·Worker 통합·핵심 E2E**를 실행한다. 아직 테스트가 없는 계층은 미구현/미실행으로 기록한다. 새 UI가 생기면 이후 루프의 회귀 집합에도 포함한다. 변경한 TS/Vue 코드의 typecheck도 확인한다.
7. **종료 판단:** 회귀 실패가 있으면 원인·영향 기능을 기록하고 그 루프에서 수정/재검증한다. 새 테스트만 통과한 상태로 다음 기능에 넘어가지 않는다. 명령·종료 코드·증거를 모두 연결한 후 루프를 완료로 기록한다.

매 테스트 실행은 같은 루프 안의 시도로 기록한다. 실패가 없던 재실행에는 ‘실패 없음’을 기록하며, 임의 실패 사유를 만들지 않는다. 리팩토링 이후 재검증은 매 루프 수행한다. 같은 코드·같은 검사에 대한 추가 반복은 새 변경/실패/우려가 있을 때만 한다.

## 테스트 도구·명령·기록

아래 실행 계획의 앱 명령을 실제 구성했다. 실행 결과는 VALIDATION의 하네스 report에 연결한다.

| 검사 | 사용할 도구·예정 명령 | 역할 |
| --- | --- | --- |
| 순수 규칙·목록 상태 | `pnpm run test:unit` → Vitest run | 입력 경계·정규화·토큰·클라이언트 상태 규칙 |
| Worker/정책/저장/경쟁 | `pnpm run test:integration` → Vitest + 기존 Cloudflare 플러그인 | 폐기 가능한 실제 D1/R2와 좁은 실패 대역. [Worker 스킬](../.agents/skills/uploader-worker-checks/SKILL.md) 기준 적용 |
| 화면·서버 연결 | `pnpm run test:e2e` → Playwright Chromium | 실제 로컬 API, 상태 전이·잠금·수동 재시도. [UI 스킬](../.agents/skills/uploader-ui-checks/SKILL.md) 기준 적용 |
| 정적 검사·번들 | `pnpm run typecheck`, `pnpm run build` | Vue/Worker 타입·배포 자산 구성 확인 |
| 단계 종료·최종 회귀 | `pnpm run check` | 이미 작성한 하네스의 5개 검사를 연결. 마지막 루프의 전체 검사와 겹치면 결과를 재사용 |

개별 Red/Green은 해당 파일/이름을 지정한 CLI로 실행하고, 마지막 재검증에는 누적된 회귀 집합을 포함한다. 자동 retry로 최초 실패를 감추거나 빈 테스트를 통과시키는 옵션은 사용하지 않는다. 테스트 구성 전에는 기존 `check`의 종료 2/blocked를 유지하고 성공으로 포장하지 않는다.

초기에는 테스트가 있는 계층만 실행하며 없는 계층을 통과로 세지 않는다. 모든 계층이 준비되면 전체 `check`를 단계 종료에 사용한다. 현재 하네스는 stdout/종료 코드·실행별 JSON을 수집하며, TDD의 실패 원인·리팩토링 판단·TC/V 대응은 TDD_LOG에 사람이 읽을 수 있게 남긴다. 로그만으로 테스트 범위나 기능 완료를 자동 판단하지 않는다.

기록은 [TDD_LOG](./TDD_LOG.md)의 루프 원장, [VALIDATION](./VALIDATION.md)의 실제 검증 원장, `.docs/verification/`의 실행 증거를 연결한다. 테스트 더미 데이터만 사용하고 비밀값·파일 본문·로컬 DB 자체는 기록/커밋하지 않는다.
