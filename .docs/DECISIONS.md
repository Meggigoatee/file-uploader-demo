## 2026-10-23 CATEGORY-03 — 공통 팝업·개별 체크·전체 적용

- 사용자 수정: 카테고리 현재 전체 확장자를 한 버튼으로 차단/허용, 수량은 이름 바로 옆, 상단+/×로 구성원 추가/제거, 추가 팝업에서 기존 등록 확인, 사용자 카테고리 생성/이름 변경/삭제는 팝업과 확인, 개별 확장자는 고정과 같은 체크박스 UI다. 기능별 다른 조작 패턴을 만들지 않는 지시를 우선한다.
- 구현: 체크=차단/체크 해제=허용. 카테고리 전체가 차단 상태이면 단일 버튼이 ‘전체 허용’, 그 외에는 ‘전체 차단’이다. 일부 차단이면 다음 동작은 전체 차단이며 빈 카테고리는 비활성이다. 구성원 목록의 현재 전체에 적용한다.
- 기본 분류도 구성원 추가/제거를 세션별 DB에 보존한다. 5개는 새 세션의 기본값이며 이후 고정 개수가 아니다. 기본 이름·카테고리 자체 삭제는 보호한다. 소속 제거는 정책을 바꾸지 않고, 사용자 카테고리 삭제는 확인 후 현재 소속 확장자를 모두 허용하는 이전 사용자 답변을 유지한다.
- 추가 입력은 정규화 후 같은 카테고리 중복을 막고, 다른 카테고리/기존 차단 정책 등록은 구분해 안내한다. 같은 확장자의 여러 카테고리 소속은 허용한다. 생성/이름 변경은 이름만 받아 소속을 덮어쓰지 않는다.
- 작은 ExtensionToggle/ModalDialog 컴포넌트로 공통 조작·native dialog 포커스/취소를 공유한다. 기존 사전 클릭으로 추가 입력을 채우던 동작은 체크박스 조작으로 대체한다. 로컬만 검증하고 배포하지 않는다.

## 2026-10-23 CATEGORY-01 카테고리 구현 확정

- 사용자 명시적 요청: USER-04a/04b 필터·일괄 차단/해제 구현, 기본 사진/영상/음성/문서의 각 항목을5개로 확장, 사용자 카테고리 생성/삭제/차단·허용. 카테고리 삭제는 소속 확장자의 차단도 해제한다는 추가 답변을 받았다.
- AI 설계: 이름·구성원 편집을 제공하고 세션별 D1에 저장한다. 이름30자·구성원50개 제한은 작은 데모용 설계값이다. 생성/편집은 분류만 변경하며 기존 차단은 바꾸지 않는다. 기본 분류는 편집/삭제하지 않는다.

- 필터는 custom 목록의 조회만 바꾸고 고정7개는 유지한다. 일괄 차단은 200개 한도를 넘으면 전부 거절하며 같은 DB의 동시 요청에도 상한을 유지한다. 편집/허용/삭제는 batch rollback 대상이다. 세션별 정책·T·과거 완료 결과·전역 누적 예산은 유지한다.

## 2026-10-22 TDD 실행 계획과 승인 절차

후속 사용자 확인 반영: Cloudflare 실제 장애·계정/리소스 한도 초과의 응답을 동일하게 재현할 수 있다고 보장하지 못하므로 해당 모방 검사를 제외한다. 임의 Error나 앱의 503을 Cloudflare 응답으로 취급하지 않는다. 앱 자체 D1 누적 예산의 실제 거절, 정책 불변식 오류, 브라우저 통신/응답 전달 제어는 구분해 유지한다. TC08/TC10/TC16 및 V17/V35/V40의 수행 범위를 좁혔으며, 앱 일반 오류 처리 설계는 유지하고 실제 제공자 장애 동작은 미검증으로 남긴다. 이후 사용자가 수정 계획을 승인해 위 실제 구현으로 이어졌다.

- 사용자 지시: 구현 순서는 AI가 정하되 합의/문서화된 범위만 구현한다. TDD 기반으로 매 루프 실패 이유·리팩토링·재시험과 기존 기능 회귀를 확인한다. 핵심 구현의 테스트 계획을 먼저 정리하고 사용자 승인 후 실제 코드를 작성한다.
- AI 실행안: 최소 실행 구성 → 공유 규칙 → 정책 DB/API → 실제 업로드/예산 → 정책 화면 → 다중 업로드 UX → 교차 회귀 → 조건부 옵션 → 배포·제출 순서. 핵심 테스트 TC01~TC19를 기존 V01~V40에 대응시켰다. 조건부 V31은 필수 범위로 바꾸지 않는다.
- 루프 절차: 실제 Red와 원인 분류/메시지 기록 → 최소 Green → 동작 유지 리팩토링 → 현재 기능의 누적 회귀·typecheck → 결과 기록. 리팩토링 항목이 없으면 이유를 기록하고 회귀 검사는 수행한다. 회귀 실패를 남긴 채 다음 기능으로 넘어가지 않는다.
- 당시 계획 작성 단계에서는 승인 대기였고 문서/양식만 작성했다. 후속 승인 뒤 앱 테스트·코드·설정·SQL을 작성했다. 설치 버전과 선정 스킬은 유지했다. 자세한 순서·관찰 기준은 [TDD_PLAN](./TDD_PLAN.md), 실제 루프는 [TDD_LOG](./TDD_LOG.md)를 따른다.

- 고정 체크박스는 원본 요구대로 check/uncheck 시 DB에 저장한다. 매번 별도 확인창을 요구하지 않는다.
- 저장 중 표시·해당 조작 잠금·서버 성공 후 확정·실패 시 이전 값 복구로 일관성을 확보한다. 저장 응답 유실은 정책 GET으로 재동기화한다.
- 카테고리 일괄 변경을 구현한다면 명시적인 일괄 동작 버튼과 대상 수 등 직접적인 안내를 검토한다. 이번에는 확인 모달/별도 미리보기 화면을 기능으로 추가하지 않는다. 대량 해제의 별도 확인은 미래 대안이다.
- 검색은 이미 등록된 고정/커스텀 목록을 각 영역에서 확인한다. 고정 7개를 커스텀 영역에 섞지 않는다. 고정 항목이 unchecked라면 ‘등록됨’과 ‘차단 중’을 구분한다. 서버 중복 검사는 계속 필요하다.
- 초기에는 추가 입력을 등록 확인에도 재사용했으나 2026-10-22 후속 지시로 별도 입력으로 분리했다. 대표 사전 클릭은 추가 입력값만 채운다. 같은 화면의 전송 그룹 처리 중 정책 변경을 잠그는 것은 조작 혼선을 줄이기 위한 설계다. 다른 방문자의 변경과 서버의 T 판정은 아래 기준을 유지한다.

## 업로드 정책의 단일 판정 시점

파일 수신·기본 검증 후, 저장 전 서버가 D1 정책을 읽어 판정하는 순간을 **T**로 삼는다. 업로드 한 번은 그때 읽은 정책 스냅샷으로 판정한다. 이후의 정책 GET은 현재 설정을 위한 조회이고, 과거 업로드 결과를 다시 판정하는 근거로 쓰지 않는다.

| 상황 | 처리 |
| --- | --- |
| 프론트 사전 검사 후, T 전에 허용→차단 | 서버가 거절. 파일 미저장, 최신 차단 이유 표시 |
| T에서 허용, R2 저장 중 허용→차단 | T의 허용 판정으로 저장 계속. 새 정책은 다음 업로드/재시도에 적용 |
| 이미 성공 응답을 받은 뒤 정책 변경·재조회 | 완료 결과 유지. 현재 설정만 갱신 |
| DB 정책/예산 조회·저장 실패 | R2 저장 전 중단, 성공으로 표시하지 않음 |
| 실패 항목을 수동 재시도 | 새 업로드이므로 새 T의 최신 정책으로 판정 |

이 기준은 **진행 중 파일에 정책 변경을 소급하지 않는 AI 설계안**이다. 최신 정책과 저장 완료를 하나의 원자적 작업으로 묶는 보장은 하지 않는다. 완료 직전에 정책을 재조회하는 방식도 재조회와 저장/응답 사이의 변경 경쟁을 완전히 없애지는 못한다. 더 강한 기준은 정책 버전·잠금·작업 상태/복구 설계를 요구하므로 대안으로 둔다.

로그에는 requestId·정책 판정 시각·결과 코드를 남기는 최소안을 사용한다. 시각은 진단 정보이며 DB의 버전 번호나 재현 가능한 정책 이력이라고 주장하지 않는다.

## 성공은 보수적으로 확정, 재업로드는 수동

- 정상 API 성공 응답은 R2 put 완료와 반환 객체 크기 확인 뒤에만 반환하는 설계이다. 전송 100%, 파일명/키의 존재, 정책 GET 결과만으로 업로드 성공을 추정하지 않는다.
- 프론트는 정상 성공 응답을 확인한 경우만 성공으로 확정한다. 타임아웃·네트워크 단절·응답 파싱 실패는 ‘완료를 확인하지 못했습니다. 다시 업로드해 주세요’로 처리한다.
- 이는 UI에서 실패/재시도 대상으로 다룬다는 뜻이다. 서버에도 파일이 없다고 단정하지 않는다. 정상 저장 후 응답만 유실됐을 수 있다.
- 자동 재시도와 상태 조회로 결과를 추정하는 기능은 두지 않는다. 사용자가 해당 실패 항목만 수동 재시도하고 성공 항목은 유지한다.
- 같은 파일이 다시 저장되거나 응답 유실 객체가 남을 수 있다. 이 한계를 문서에 남기고 UUID·비공개 저장·아래 누적 저장 예산으로 영향을 제한한다. 정확히 한 번 저장을 보장하지 않는다.
- 서버가 저장 실패를 확인했고 해당 요청에서 만든 키가 있으면 정리를 시도할 수 있으나, 통신 실패 시 정리까지 보장했다고 표현하지 않는다.

## 무료 제공량과 프로젝트 한도

2026-10-21 공식 문서 확인값이다. 무료 제공량은 제품별 단위가 다르며 실제 계정 플랜·다른 리소스 사용량은 아직 확인하지 않았다.

| 제품 | 확인한 무료 기준 | 출처 |
| --- | --- | --- |
| Workers Free | 요청 100,000회/일, HTTP CPU 10ms, 메모리 128MB | [Workers Limits](https://developers.cloudflare.com/workers/platform/limits/) |
| D1 on Workers Free | 읽은 행 500만/일, 쓴 행 10만/일, 저장 합계 5GB | [D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/) |
| R2 Standard | 저장 10 GB-month/월, Class A 100만/월, Class B 1,000만/월 | [R2 Pricing](https://developers.cloudflare.com/r2/pricing/) |

R2 무료 제공량은 초과 사용 비용이 정의된 요금 체계이며 무료량만으로 자동 중단을 가정하지 않는다. 10 GB-month는 순간 최대 용량과 같은 단위가 아니다. Workers/D1의 Free 제한 도달 시 동작과 R2의 과금 체계를 혼동하지 않는다.

### AI의 프로젝트 전용 한도 설계안

- 기존 기준안: 파일당 5 MiB, 요청 본문 6 MiB, 목록 10개, 전송 동시 수 1. 플랫폼 한도와 같게 잡은 값이 아니라 작은 데모를 위한 앱 설정안이다. 실제 CPU·메모리를 확인한 뒤 파일 상한을 낮출 수 있다. 5 MiB 파싱이 CPU 10ms 안에 든다는 검증은 아직 없다.
- 누적 저장 예산 기본안: **총 256 MiB와 저장 시도 500회**. 프로젝트 전용 빈 버킷/예산을 기준으로 한다. 계정 전체의 무료 잔량을 뜻하지 않는다. 설정값은 구현 전 조정할 수 있다.
- D1의 단일 예산 행에서 파일 크기와 저장 시도 1회를 **조건부 갱신으로 먼저 원자적 예약**한다. 예약 성공이 확인된 요청만 R2 put을 한 번 시도한다. 실패·응답 유실·재시도도 예산을 소비하며 자동 환급하지 않는다.
- 예산을 시간 경과/재배포/파일 만료만으로 자동 초기화하지 않는다. 상한에 도달하면 업로드 중단 사유를 안내한다. 별도 관리자 화면은 만들지 않는다. 확인된 정리 후 예산 재설정은 운영 작업이다.
- 이 보수적인 누적 방식은 별도 업로드 작업 테이블 없이도 앱 경로에서 시도하는 저장량을 제한한다. 최초 버킷의 기존 데이터, 다른 프로젝트/직접 API의 사용, 전체 계정 요금까지 제어하지 않는다. 배포 전 계정 사용량과 전용 버킷 상태를 확인한다.
- D1 제한/장애 시 예산 예약을 실패 처리하고 업로드를 계속하지 않는다. 공개 정책 조회의 무제한 가용성을 보장하지 않으며 무료량 소진 시 제한에 걸릴 수 있다.
- Edge rate limit은 정확한 누적 회계 대신 쓰지 않는다. SHA-256 전체 검사·파일 내용 파싱·상태 polling도 이번 기본안에 추가하지 않는다.

업로드 예산 행은 용량 제어용이며 개별 파일의 저장 성공 상태를 나타내지 않는다. 파일별 상태 조회 테이블을 보류한 결정과 구분한다.

## DB 선택 근거 — SQLite 문법의 Cloudflare D1 선택

상태: 선택 이유를 설명한 이전 대화에서는 제안이었으며, 후속 사용자의 요구 적합성·구성 단순성 우선 결정에 따라 **D1을 현재 구현 기준안으로 선택**했다. SQLite도 관계형 DBMS이다. 배포 모델은 Worker의 로컬 디스크에 SQLite 파일을 직접 두는 방식이 아니라 **Cloudflare가 관리하고 Worker 바인딩으로 접근하는 D1**이다. D1은 SQLite SQL semantics를 제공한다. [D1 소개](https://developers.cloudflare.com/d1/).

### 이 과제에서 우선 제안한 이유

1. **Cloudflare 배포 연동을 줄인다.** Workers/D1/R2를 같은 플랫폼에서 설정할 수 있다. 외부 DB 호스팅 선택, 접속 정보·드라이버·연결/풀 설정을 별도로 추가하는 범위를 줄일 수 있다고 판단했다. 특정 분 단위 절감이나 더 빠른 구현을 실측한 것은 아니다.
2. **모델이 작고 단순하다.** 정책은 최대 207행, 저장 예산은 1행이며 실제 파일은 R2에 둔다. 주요 작업은 조회·단건 변경·조건부 INSERT/UPDATE로, 현재 요구에서 PostgreSQL/MySQL 고유 기능이 필요하다고 판단한 부분은 없다.
3. **필요한 정합성 수단을 사용할 수 있다.** PK/UNIQUE/CHECK, prepared statement, 조건부 원자적 쓰기로 중복/상한/예산을 처리한다. 정합성은 실제 마이그레이션·영향 행 수·동시 요청 검증으로 확인해야 한다. D1의 batch/트랜잭션 API가 일반적인 서버 DB의 API와 같다고 가정하지 않는다.

### MySQL/PostgreSQL도 가능한 대안

Cloudflare Hyperdrive는 PostgreSQL/MySQL과 관리형 제공자를 지원한다. 따라서 Cloudflare 사용이 D1을 강제하는 것은 아니다. 이 경로를 선택한다면 DB 제공자·자격증명·드라이버·연결 관리와 플랫폼 지원 기능을 확인한다. MySQL/PostgreSQL에도 관리형 서비스가 있으며 직접 DB 서버를 운영해야만 한다고 비교하지 않는다. [Hyperdrive 지원 DB](https://developers.cloudflare.com/hyperdrive/reference/supported-databases-and-features/).

현재는 새 저장소에서 시작하고 사용자 DB 숙련도/기존 DB 계정은 알려지지 않았다. 이미 익숙하고 준비된 MySQL/PostgreSQL 환경이 있으면 D1보다 도입 부담이 낮을 수 있으므로 선택을 다시 평가한다.

### 한계와 선택을 바꿀 조건

- D1 단일 DB는 쿼리를 한 번에 하나씩 처리하고 과도한 요청은 대기/오버로드를 일으킬 수 있다. 데이터가 207행이라는 사실만으로 동시 처리 성능을 보증하지 않는다. [D1 동시성·처리량](https://developers.cloudflare.com/d1/platform/limits/#concurrency-and-throughput).
- 예산 단일 행은 모든 업로드가 갱신하므로 경합 지점이다. 대규모 동시 업로드가 목표가 되면 DB 엔진과 예산 모델을 함께 재검토한다. 같은 단일 행의 경합이 DB 변경만으로 없어지는 것은 아니다.
- 긴/복잡한 트랜잭션, 조직 표준 DB·기존 시스템 연동, 많은 동시 쓰기가 실제 요구로 들어오면 MySQL/PostgreSQL의 관리형 구성을 우선 비교한다. SQLite가 조인이나 트랜잭션을 지원하지 않는다고 설명하지 않는다.
- Cloudflare 결합과 D1 API/한도도 선택 비용이다. 다른 DB로 바꾸면 SQL 차이·타입·마이그레이션·바인딩/드라이버·동시성 검증을 확인해야 한다. 무수정 전환을 보장하거나 미리 범용 Repository 계층을 만들지 않는다.
- 아직 D1 계정/배포 연결·성능을 검증하지 않았다. 이번 기준안 선택은 요구 범위·배포 구성의 적합성에 따른 판단이며 성능/비용 우위의 실측 결과가 아니다.
