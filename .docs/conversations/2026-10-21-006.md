# 대화 006 — 사용자 기능 채택과 백엔드 보완 제안

- 날짜/시간대: 2026-10-21, Asia/Seoul.
- 최초 시각 확인: 21:53 KST. 실제 사용자 전송 시각은 제공되지 않음.
- 단계: 기능 범위 결정 및 추가 브레인스토밍. 구현 요청 없음.

## 사용자 입력 원문

```text
카테고리 필터·일괄 변경은 시간이 허락하면 구현하는 것으로 하고, 나머지 사용자 제안은 핵심 추가 기능으로 분류한다.
지금 제안 사항은 프론트엔드 쪽으로 치우쳐져 있다. 보안, 데이터 전송, 파일 검사, DB 저장 상태 등에 있어서 네가 더 제안하고 싶은 사항이 있나?
```

## 입력 의도와 사용자 결정

- USER-01/02/03/05/06 다중 선택·드롭·파일별 진행/결과·대표 확장자 사전 분류·전송 전 검사를 핵심 추가 기능으로 채택.
- USER-04a/04b 카테고리 필터·일괄 변경은 시간 여유 시 구현. 대표 분류 사전은 이 선택 기능과 독립적으로 유지.
- 보안·전송·파일 검사·DB 저장 상태에 대한 AI의 추가 제안을 요청. 새 제안을 자동 채택하거나 코드 구현을 승인한 것은 아님.

## AI 중간 응답 1

> 카테고리 필터·일괄 변경은 시간 여유가 있을 때 구현하는 항목으로, 나머지 사용자 제안 5개는 핵심 추가 기능으로 반영하겠습니다. 보안·전송·파일 검사·저장 상태에서는 6시간 범위에 맞는 보완책을 제안하되, 제 제안은 별도 후보로 남기겠습니다.

## AI 중간 응답 2

> 백엔드 후보 중에서는 업로드별 접수 ID로 저장 결과를 다시 조회하고 중복 재전송을 줄이는 기능이 파일별 결과 UX와 잘 연결됩니다. 다만 이를 채택하면 업로드 상태를 저장할 테이블과 DB·파일 저장소 간 실패 처리가 추가됩니다.
>
> 크기 제한·격리 저장·제한된 시그니처 검사는 기존 후보를 구체화하고, 접수 ID·상태 조회·체크섬 검증은 새 제안으로 구분하겠습니다. 숫자로 시간을 단정하지 않고 변경 범위와 검증 부담을 함께 적겠습니다.

## 도구·자료 및 작업 결과

- PowerShell/rg: 현재 PLAN/FEATURE/DESIGN/검증·기록 확인.
- clock.curr_time: KST 기록 기준 확인.
- web.run: OWASP File Upload, Cloudflare D1 batch, R2 put/checksum, Workers Rate Limiting 공식 자료 확인. 제안 우선순위는 AI 판단이며 공식 자료의 개발 시간 수치를 사용한 것이 아님.
- apply_patch: PLAN에 사용자 기능 5개와 조건부 2항목 반영, FEATURE의 출처·상태 및 AI-05~11 후보 작성, DESIGN/VALIDATION/CONSIDERATIONS/README/로그 갱신.
- 한 번의 문서 패치에서 기존 문장 일치 실패로 반영되지 않았음을 확인한 뒤, 정확한 문장으로 나눠 재적용. 작성 중 섞인 비한국어 표현도 점검·정정.
- AI-05/06/07/08은 기존 K2/K7/K3/K4의 구체화, AI-09/10/11은 신규 후보. DB 상태 조회를 채택하면 초기 ‘메타데이터 테이블 없음’ 설계가 바뀌는 부담과 복구 문제를 명시.
- AI-09의 중복 방지는 같은 업로드 작업에 적용하며 파일명 중복 차단과 구분. D1/R2 간 원자성, ID-내용 바인딩, 조회 권한, 복구 필요 상태를 고려.
- 현재 사용자 기능 합의만 계획에 반영. 새 AI 후보는 미합의 상태로 유지. 신규 분 단위 견적 없음.
- 코드·설정·SQL 생성, 패키지 설치, 앱 테스트, 리소스 생성·배포 없음. 별도 스킬·서브에이전트 없음.
- 문서 검증 결과: Markdown 14개, 코드 블록을 제외한 로컬 링크 25개(앵커 포함), 깨진 링크 0개, `.docs` 밖 파일 0개. PLAN의 채택 사용자 기능 5개와 비한국어 표현 점검 결과를 확인했다. 앱 동작/성능/개발 시간 검증은 미실행이다.

## AI 최종 응답

```markdown
반영했습니다. 다중 선택·드롭·파일별 진행/결과·대표 확장자 사전 분류·전송 전 검사는 **핵심 추가 기능**, 카테고리 필터·일괄 변경은 **시간 여유 시 구현**으로 정리했습니다.

백엔드에서는 다음을 제안합니다. **1~4는 기존 AI 후보의 구체화, 5는 새 제안**입니다.

| 제안 | 해결하려는 문제 | 최소 구현 범위 |
| --- | --- | --- |
| **1. 서버의 업로드 자원 제한** | 큰 요청·과도한 파일 수로 메모리와 저장 공간 소모 | 실제 읽은 바이트 기준 본문/파일 크기 제한, 선택 개수 제한, 명확한 초과 사유 |
| **2. 격리된 파일 저장** | 원본명 경로 조작·덮어쓰기·업로드 파일 실행/노출 | UUID 저장 키, 비공개 저장소, 원본명은 표시용으로만 사용 |
| **3. 제한된 파일 시그니처 검사** | 실행 파일을 jpg처럼 이름만 바꿔 업로드 | PNG/JPEG/PDF 등 대상 형식을 정해 헤더 불일치 거절. MIME은 신뢰하지 않음 |
| **4. 정책 저장 확정과 장애 처리** | 저장 실패를 성공으로 표시하거나 DB 장애 때 차단을 우회 | DB 고유 제약·원자적 상한 검사, 저장된 값으로 응답, 불확실하면 재조회, 정책 조회 실패 시 업로드 중단 |
| **5. 업로드 접수 ID·상태 조회·중복 방지** | 저장은 됐지만 응답이 끊겨 재전송하거나 결과를 알 수 없음 | 업로드 작업 ID와 상태를 저장하고 같은 작업의 중복 실행을 제어. 연결 복구 후 결과 조회 |

크기 제한·서버 생성 파일명·격리 저장·시그니처 검사는 [OWASP 업로드 지침](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)에서도 다룹니다. 다만 **시그니처 일치는 악성코드가 없다는 보증은 아닙니다.**

특히 5번은 사용자 제안인 **파일별 결과 표시의 신뢰도**를 높입니다. 다만 업로드 작업 테이블과 상태 조회 API가 추가됩니다. R2 저장 후 DB 완료 기록이 실패하는 경우까지 다뤄야 하므로, 별도 합의가 필요한 큰 후보입니다. ‘같은 파일명’이 아니라 ‘같은 업로드 작업’의 재전송을 구분합니다.

추가 대안으로 **SHA-256 무결성 검증**과 **연속 요청 제한**도 있습니다. 전자는 바이트 일치 여부를 확인하며 악성 여부는 판별하지 않습니다. 후자는 반복 요청을 완화하지만 정확한 전역 비용 상한을 보장하지 않습니다. ([R2 체크섬 지원](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/), [Workers 요청 제한](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/))

제 의견은 **1·2·4를 기본 품질 보완으로 우선 검토하고, 3은 검사 형식을 좁혀 추가하며, 5는 구조 변경을 감수할 가치가 있는지 따로 판단**하는 것입니다. 새 제안은 [후보 문서](D:/garage/file-uploader-demo/.docs/FEATURE_BRAINSTORM.md)에만 기록했고 최종 계획에는 자동으로 추가하지 않았습니다.
```
