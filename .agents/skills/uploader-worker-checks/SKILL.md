# Worker 정책·저장 검증

이 저장소의 서버 경계를 검증하는 절차다. 기능 구현은 해당 사용자 요청이 있을 때 진행한다.

## 필요한 참조만 읽기

- API·제약·업로드 흐름을 변경하면 [DESIGN](../../../.docs/DESIGN.md)의 해당 절을 읽는다.
- 정책 경쟁·응답 유실·예산을 다루면 [DECISIONS](../../../.docs/DECISIONS.md)를 읽는다.
- 검증 범위는 [VALIDATION](../../../.docs/VALIDATION.md)의 관련 V 항목에서 선택한다. 전체 검증표를 매번 실행하지 않는다.

## 검증에서 놓치기 쉬운 경계

- 순수 정규화 규칙은 일반 Vitest로 확인한다. DB 상한·동시성·R2 저장은 격리된 실제 로컬 바인딩으로 확인한다. HTTP 성공이나 mock 호출만으로 저장을 증명하지 않는다.
- 허용 업로드는 R2에서 바이트를 다시 읽고, 거절 업로드는 객체가 늘지 않았는지 확인한다. 고정 정책·커스텀 상한은 실제 DB 행으로 확인한다.
- 동시성 검증은 같은 DB에 요청을 겹쳐 보낸다. 서로 격리된 테스트끼리 동시 실행한 결과로 200개 상한이나 예산 예약의 원자성을 입증하지 않는다(V06/V19/V35).
- T 전/후의 정책 변경은 await 가능한 테스트 경계로 제어한다. 임의 sleep에 의존하지 않는다(V20/V34). D1 작업과 R2 put이 하나의 트랜잭션이라고 가정하지 않는다.
- 예약 성공 미확인 시 put이 없어야 한다. put 실패·응답 유실 시 예산 자동 환급을 기대하지 않는다. 저장 완료와 응답 도착을 분리해 실패 경로를 검증한다(V17/V35/V36).
- 공개 데모 대신 폐기 가능한 로컬 리소스를 사용하고 테스트가 만든 데이터만 정리한다. 장애 재현에 필요한 지점만 좁게 대역 처리한다.

## 설치 버전과 실행

현재 설치는 Vitest 4.1.10, @cloudflare/vitest-plugin 1.1.2, Wrangler 4.127.1이다. 새 예제를 붙일 때 설치된 타입 정의·exports를 먼저 확인한다. 과거 pool 패키지를 설치하거나 문서 예제에 맞춰 버전을 올리지 않는다.

앱 테스트 구성 후 단건 실행은 `pnpm exec vitest run ...`을 사용한다. 전체 검증 진입점·아직 없는 스크립트의 처리·증거 위치는 [하네스 문서](../../../.docs/HARNESS.md)를 따른다. 구성 부재는 미준비로 보고하며 빈 테스트를 통과로 바꾸지 않는다.

실행 명령·관련 V 항목·DB/R2 증거·실패/미실행을 VALIDATION에 기록한다. 스킬 작성·읽기만으로 해당 기능을 검증했다고 표시하지 않는다.

출처: 이 프로젝트의 DESIGN/DECISIONS/VALIDATION을 바탕으로 직접 작성했다. 도구 사용 근거는 [Cloudflare Vitest 공식 문서](https://developers.cloudflare.com/workers/testing/vitest-integration/write-your-first-test/)이며 외부 스킬을 복사·설치한 것이 아니다.
