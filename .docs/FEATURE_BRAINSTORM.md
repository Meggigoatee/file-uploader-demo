# 핵심 추가 기능 브레인스토밍

기준: 초기 제안은 2026-10-21, 카테고리 후속 결정은 2026-10-23. 사용자5개 및 AI-01/02/03/05/06/08을 구현했고, 후속 명시적 요청으로 USER-04a/04b·분류별5개·사용자 카테고리도 로컬 구현한다. 이전 조건부 표기는 당시 이력이다. AI-04 확인 단계·AI-07 시그니처·AI-09 상태 조회와 기타 대안은 기존 미채택/보류를 유지한다. 상세 사용자 지시/AI 설계 구분은 [DECISIONS](./DECISIONS.md), [후속 계획](./CATEGORY_PLAN.md)을 따른다. 과거 시간 추정은 사용하지 않는다.

최신 논의 반영: 구성·구동 단순성을 기준으로 Workers/D1/R2 기준안을 선택했다. 합의 기능의 현재 화면·상호작용 설계는 [UI_UX.md](./UI_UX.md)를 따른다. 아래 A/B 비교와 추정은 당시 대안 기록이며, 예시 목록 수나 조작이 현재 설계와 다르면 UI_UX/PLAN을 우선한다. 새 화면 세부안을 사용자 제안으로 바꾸어 기록하지 않는다.

## 시간 추정의 근거와 한계 — 사용자 질문에 따른 정정

- 산정 방식: 작업 분해 후 각 작업에 직관적 최소/최대 시간을 배정하고 하한끼리·상한끼리 더했다. 실제 표본에서 나온 최소/최대나 통계적 신뢰구간이 아니다.
- 산정 전제: 공통 정책 API·단일 업로드 API가 준비되어 재사용 가능하고, 단순한 Vue 화면과 정적 확장자 사전을 사용하며, 설치/바인딩/배포 장애가 없는 상황을 가정했다. **이 프로젝트에는 아직 그 구현이 없다.**
- A는 기존 단건 API를 유지하고 프론트 목록·전송 상태를 추가하는 범위, B는 일괄 저장·전체 성공/실패·변경 요약까지 추가하는 범위로 잡았다. 이는 AI가 제안한 구체 범위이며 사용자와 합의된 동일한 완료 기준이 아니다.
- 사용자 기술 숙련도는 정성적으로만 고려했다. 사용자가 직접 작성하는지, AI가 작성하고 사용자가 검토하는지, 각자의 실행·검토·대기 시간을 어떻게 합치는지 정의하거나 측정하지 않았다.
- 핵심 검증 시간을 일부 넣었으나 오류 발견 후 반복 수정·재검증, 도구 대기, 원격 환경 문제를 일관된 기준으로 계산하지 않았다. ‘70~110분’처럼 좁은 숫자 범위를 신뢰할 실증 근거가 부족하다.
- MDN 확인은 관련 API와 동작을 확인하기 위한 것이며 개발 소요 시간이나 난이도 수치를 입증하지 않는다. 이전 문서 점검의 합계 확인도 산술 확인일 뿐 추정 정확도 검증이 아니다.
- 따라서 숫자만으로 B가 항상 오래 걸린다거나 A와 B를 모두 6시간 내 할 수 없다고 판단하지 않는다. 남는 비교 근거는 A의 파일별 상태 처리와 B의 일괄 정책 의미·저장 정합성 등 **작업 종류와 의존성**이다.
- 향후 범위·완료 조건·구현/검토 역할을 먼저 맞추고 공통 작업의 중복을 제거해 다시 산정한다. 명시적 구현 요청 이후 첫 구현·검증의 실제 소요 시간을 얻으면 보정한다. 추정을 확인한다는 이유로 지금 코드나 실험 프로젝트를 만들지 않는다.

## 합의 및 기록 방식

- 사용자 제안은 검토할 요구/아이디어로 기록한다. 구체적인 축소안까지 사용자가 동의했다고 간주하지 않는다.
- AI는 각 제안에 대한 찬성·조건부 찬성·보류와 이유를 제시한다. 사용자의 제안에 덧붙인 구현 방식은 AI 세부안으로 표시한다.
- **사용자와 AI가 같은 구현 범위를 합당하다고 판단한 항목만 PLAN의 확정 추가 기능으로 옮긴다.** 다른 항목은 이 문서의 대안으로 유지한다.
- 상태는 `제안 → 평가/범위 조정 → 합의 → 최종 계획 반영`으로 관리한다. P0/P1만으로 합의를 표시하지 않는다.
- 사용자는 처음에는 두 방향의 범위·비용 비교를 요청했고, 이후 USER-01/02/03/05/06을 핵심 추가 기능으로, USER-04a/04b를 시간 여유 시 구현으로 결정했다. 이를 과거 A/B 묶음 전체나 AI 제안의 일괄 승인으로 확대하지 않는다.

## 방향 A — 업로드 UX 중심 (과거 비교안)

검토 묶음: USER-01/02/03/06 + AI-01. AI-02는 비용을 따로 보고 선택한다. 정책 관리는 원본의 고정/커스텀 구성을 유지하고 AI-03 또는 읽기 전용 카테고리는 별도 선택한다.

흐름: `선택 또는 드롭 → 파일별 사전 판정 → 전송할 항목 확인 → 순차 전송 → 파일별 결과`.

- 다중 선택은 브라우저 목록의 개념이고 API는 여전히 요청당 파일 하나다. 기존 본문 6 MiB/파일 5 MiB 제안과 양립한다. 목록 최대 개수(예: 10개)는 AI 제안값이며 아직 확정하지 않는다.
- 선택과 드롭은 동일한 검사·목록 등록 함수를 사용한다. 폴더/파일 외 데이터는 지원 범위를 안내한다. 드롭 존 때문에 파일이 새 탭에서 열리지 않도록 기본 동작을 처리하고 키보드 선택을 유지한다.
- 파일별 상태 예: 준비/사전 차단/전송 중/서버 확인 중/성공/서버 거절/저장 여부 불명확. 한 파일 거절로 나머지 정상 파일을 모두 실패시키지 않는 동작을 제안한다.
- 전송률은 XMLHttpRequest의 upload progress 사용을 후보로 한다. 길이를 계산할 수 없으면 숫자를 꾸며내지 않고 진행 중 상태만 표시한다. 작은 파일은 0→100으로 빨리 변할 수 있다.
- 전송 100%는 ‘서버 확인 중’이다. 서버 검증과 R2 저장 성공 응답을 받은 뒤에만 ‘완료’이다. 전송률만으로 완료 시각이나 남은 시간을 확정하지 않는다.
- 사전 검사 결과는 예측이다. 전송 직전 최신 정책을 재조회해 대기 파일을 다시 검사하는 안을 제안한다. 그 이후 다른 사용자의 정책 변경은 서버 최종 판정에 따른다. 차단 파일 전송 감소는 기대하지만 서버 실패가 없어지는 것은 아니다.
- AI-02 채택 시 서버가 명확히 실패를 응답한 항목의 재시도와 통신 단절로 결과가 불확실한 항목을 구분한다. 후자는 중복 저장 가능성을 표시하며 자동 재시도하지 않는다.

미검증 초기 배분: **70~110분**. 다중 목록 20~30, 드롭 10~15, 파일별 진행/결과 20~30, 사전 검사 10~20, 연결 검증 10~15분을 배정했었다. 같은 목록 로직을 재사용하는 가정이다. AI-02의 별도 10~20분도 같은 방식의 미검증 값이다. 이 수치의 일정 판단 사용은 보류한다.

이것은 업로드 UX 작업 묶음의 비용이며, 정책 DB/API·업로드 서버·배포·문서의 전체 비용이 아니다. 기존 55분 단일 화면 연결 중 업로드 부분을 대체하므로 기존 360분에 단순 가산하거나 6시간 내 완료를 보장할 수 없다.

검증 포인트: 선택과 드롭 결과 동등, 허용/차단 혼합 목록, 파일별 독립 결과, 전송 100%와 저장 완료 구분, 중간 정책 변경, 네트워크 결과 불확실 상태. 진행률의 느린 변화는 브라우저 네트워크 제한으로 확인하고 서버 저장 지연은 별도로 검증한다.

## 방향 B — 정책 관리 UX 중심 (과거 비교안)

검토 묶음: USER-04a/04b/05 + AI-04. 업로드는 초기 단일 파일 UI를 유지하며 USER-06은 공통 후보로 따로 검토한다. 다중 선택/드롭/파일별 진행률은 이 안의 기본 비용에 포함하지 않는다.

흐름: `카테고리/대표 목록 보기 → 현재 차단 상태와 변경 대상 확인 → 일괄 적용 → 저장 결과 확인`.

- 알려진 분류는 코드의 작은 정적 사전으로 시작한다. 별도 카테고리 DB/관리 화면/AI 자동 분류는 필요하지 않다. 사진(jpg/jpeg/png/webp), 영상(mp4/webm), 음성(mp3/wav), 문서(pdf/txt/docx/xlsx/pptx)는 설명용 예시이며 채택 목록은 미정이다. 사전에 없는 임의 확장자는 ‘기타’로 표시한다.
- 대표 목록은 안내 데이터이고 등록된 차단 정책만 200개 상한에 포함한다. 최초 렌더링만으로 대표 목록을 DB에 넣거나 고정 7개를 체크하지 않는다.
- ‘카테고리 전부 차단’은 이 블랙리스트 모델에서 모든 이미지/영상 형식을 차단한다는 의미가 될 수 없다. ‘대표 이미지 확장자 N개 차단’처럼 실제 적용 대상을 드러내는 표현을 제안한다. 확장자 이름의 분류이지 실제 파일 내용의 판별이 아니다.
- custom 등록은 차단, 삭제는 해당 차단 해제라는 기존 모델을 유지할 수 있다. 고정 항목은 custom으로 옮기지 않고 체크 값만 바꾼다. 이미 차단된 값은 중복 계산하지 않고 신규 custom 수를 상한에 반영한다.
- 카테고리 적용 전 실제 변경 대상과 저장 후 총수를 보여주는 AI-04를 검토한다. 이미 수동으로 등록한 jpg도 카테고리 해제로 삭제할지 명확히 해야 한다. 최소안은 적용 대상 전체를 명시하고 해제하되 등록 출처/과거 상태 복원은 지원하지 않는 방식이다.
- 상한 초과면 전체 거절, DB 실패면 일부만 저장되지 않도록 전체 롤백하는 방식을 제안한다. 여러 단건 API 호출을 UI에서 반복하는 것만으로 원자적 일괄 변경을 구현했다고 보지 않는다.
- 별도의 카테고리 차단 boolean은 저장하지 않고 실제 확장자 정책으로 ‘없음/일부/대표 목록 전체’ 상태를 계산하는 안을 제안한다. 그래야 두 종류의 상태가 어긋나지 않는다.

미검증 초기 배분: **90~140분**. 필터/대표 사전 20~30, 일괄 정책 저장 35~60, 변경 요약 10~15, 상한/실패/동시성 연결 검증 25~35분을 배정했었다. 단건 정책 API와 UI 일부를 대체한다. USER-06의 별도 10~20분도 같은 방식의 미검증 값이다. 이 수치의 일정 판단 사용은 보류한다.

검증 포인트: 대표 사전과 실제 정책 분리, 초기 고정 unchecked 유지, 부분 차단 상태, 수동 등록 값 해제 의미, 고정/custom 중복, 200개 경계, 저장 중 실패 시 전체 일관성, 필터 변경만으로 DB가 바뀌지 않음.

### AI-09의 DB·파일 저장 상태 쟁점 (보류한 대안)

- 목표는 동일 파일명 차단이 아니라 **같은 업로드 작업의 재전송 식별**이다. 사용자가 의도한 별도 업로드를 임의로 합치지 않는다.
- 작업 ID와 상태를 DB에 보관하고 고유 제약·조건부 갱신으로 중복 실행을 제어하는 안이다. 상태 후보는 처리 중/저장 완료/거절·실패/복구 필요. 성공 표시에는 실제 파일 저장과 완료 기록의 확인이 필요하다.
- 같은 ID로 다른 바이트를 보내면 충돌로 거절할 기준이 필요하다. 파일명·크기만으로 같은 내용을 증명할 수 없으며 해시/불변 바인딩 등의 선택을 설계해야 한다.
- `DB 처리 중 기록 → R2 저장 → DB 완료 기록` 사이에 실패가 생길 수 있다. **D1 트랜잭션은 R2 저장까지 함께 묶지 않는다.** 완료 기록 실패를 무시하고 새 업로드를 하면 중복·고아 객체가 남을 수 있다.
- 최소 복구안은 같은 ID의 결정된 객체 키를 확인해 상태를 조정하고, 명확한 실패의 미완료 객체를 정리 시도하며, 확인/정리도 실패하면 복구 필요 상태를 남기는 방식이다. exactly-once 보장이나 별도 대형 재처리 시스템을 제안하지 않는다.
- 상태 조회에는 작업 접근 권한 범위도 정해야 한다. 추측 어려운 ID를 사용자 인증과 동일시하지 않으며 원본명·내부 오류·객체 URL을 공개 목록으로 노출하지 않는다.
- 초기 DESIGN은 업로드 메타데이터 테이블이 없는 최소안이다. AI-09 채택 시 테이블·보관 기간·상태 조회 접근 범위·복구 검증을 함께 추가해야 한다. 현재는 스키마나 API를 확정하지 않는다.

### 검사·전송 대안의 한계와 근거

- AI-07의 헤더 일치는 무해함을 증명하지 않는다. 미지원 형식을 검사 완료로 표시하거나 unchecked exe를 숨은 규칙으로 무조건 차단하지 않는다. 크기 제한·서버 생성 이름·격리 저장·시그니처 검사 방향은 [OWASP 업로드 안내](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)를 참고했다.
- AI-08의 단건 제약/조건부 쓰기는 상한 검사를 선조회한 뒤 나중에 저장하는 경쟁을 피하도록 설계한다. D1의 여러 문장 batch는 실패 시 롤백되지만 각 SQL의 조건/영향 행 수를 확인해야 한다. [D1 API](https://developers.cloudflare.com/d1/worker-api/d1-database/).
- AI-10에 Workers Rate Limiting binding을 쓴다면 지역별·느슨한 일관성의 제한이므로 정확한 전역 비용 상한으로 설명하지 않는다. IP 공유 오탐과 임의 변경 가능한 식별자의 우회 가능성을 고려하며 기준 수치와 키는 미정이다. [Cloudflare Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/).
- AI-11은 바이트 무결성 확인이다. 공격자가 파일과 기대 해시를 함께 제출할 수 있어 악성 검사나 인증을 대신하지 않는다. R2 put의 체크섬 옵션 지원을 확인했으나 HTTPS와 별도로 도입할 실익은 판단해야 한다. [R2 API](https://developers.cloudflare.com/r2/api/workers/workers-api-reference/).
- 백신/샌드박스, Office 매크로 분석, ZIP 내부 재귀 검사, 대용량 분할·재개, 전역 예산 회계 시스템은 현재 대안으로 남긴다.
