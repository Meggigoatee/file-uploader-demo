# 로그인 없는 세션별 정책 분리 검토

2026-10-23 검토 당시의 제안과 비교 기록이다. 이후 사용자가 익명 쿠키+D1 정책 분리·새 세션 초기값·새로고침 유지·최소 로컬 TDD 구현을 선택했다. 실제 구현은 [DESIGN](./DESIGN.md)의 세션 테이블·API와 [TDD_LOG](./TDD_LOG.md)의 SESSION-01을 따른다. 아래 제안 중 24시간 만료·새 데모 시작 UI·정리/발급 상한·스케줄은 채택하지 않았다. 세션 쿠키의 브라우저 수명을 사용하고 서버 DB 자동 정리는 미구현이다. 배포하지 않는다.

## 현재 문제와 목표

- `extension_policies`는 extension 단독 PK이며 모든 요청이 같은 행을 읽고 쓴다. `0001_initial.sql`의 `INSERT OR IGNORE`는 기존 체크 상태를 보존한다. 서버를 다시 켜거나 새 방문자가 접속해도 최초 unchecked 상태를 보장하지 않는다.
- 목표는 새 익명 세션마다 고정 7종 unchecked·커스텀 0개로 시작하고, 같은 세션의 새로고침에서는 변경값을 유지하며, 다른 세션의 조회·수정·업로드 판정에 영향을 주지 않는 것이다.
- 접속할 때 전역 DB를 초기화하면 다른 방문자의 설정을 지우므로 해결책으로 채택하지 않는다. 브라우저 화면만 초기화하면 서버 정책과 달라진다.

## 대안 비교

| 방식 | 격리 단위·유지 | 이점 | 비용·한계 |
| --- | --- | --- | --- |
| 서버 발급 익명 쿠키 + D1 정책 | 브라우저 프로필의 해당 호스트 쿠키 저장소. 새로고침·같은 브라우저 탭은 공유 | 기존 동일 출처 fetch/XHR에 연결하기 쉽고 HttpOnly 적용 가능. 별도 인증 서비스/라이브러리 불필요 | 같은 프로필을 함께 쓰는 사람은 구분하지 못함. 새 탭이 새 체험이 되지는 않음 |
| 서버 발급 토큰 + sessionStorage + D1 정책 | 원칙적으로 탭별. 새로고침 유지 | 한 브라우저에서 독립 시연을 여러 개 열기에 적합 | 모든 정책 fetch/업로드 XHR에 토큰 전달 필요. JS 접근 가능. opener로 열린 탭은 초기 저장소가 복사될 수 있어 단순 sessionStorage만으로 항상 새 세션이라고 보장할 수 없음 |
| 브라우저 저장소에 정책만 보관 | 탭 또는 브라우저 로컬 | 구현이 작아 보임 | 서버 DB 정책 적용 요구를 충족하지 못함. 클라이언트 전달 정책을 신뢰하면 서버 검증 의미가 바뀌므로 제외 |

우선 권고는 **익명 쿠키 + D1**이다. 서로 다른 방문자 브라우저의 설정 충돌을 줄이려는 요청에 가장 작은 변경으로 대응한다. 같은 브라우저의 탭까지 독립시키는 것이 목표라면 두 번째 방식을 선택해야 한다. 로그인 없이 실제 사람을 식별하는 것은 두 방식 모두 보장하지 않는다.

브라우저 근거: [MDN sessionStorage](https://developer.mozilla.org/en-US/docs/Web/API/Window/sessionStorage)는 탭별 저장, 새로고침 유지, opener 복사를 설명한다. [MDN Set-Cookie](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie)는 HttpOnly·Secure·SameSite 및 브라우저 세션 복원 시 쿠키 복원 가능성을 설명한다.

## 권고안의 최소 구성

1. UI 최초 진입에서 익명 세션 초기화 요청을 한 번 완료한 뒤 정책 조회를 시작한다. 예시 API는 `POST /api/session`이다. 유효한 기존 쿠키가 있으면 같은 세션을 유지하고, 없으면 서버가 암호학적 난수 토큰을 발급한다. 클라이언트가 임의로 고른 ID를 세션 생성 키로 채택하지 않는다.
2. `anonymous_sessions`에 토큰 해시·생성/만료 시각을 저장한다. 토큰 원문은 쿠키로만 전달하고 URL·본문·로그에 노출하지 않는다. HTTPS에서는 HttpOnly·Secure·SameSite=Lax, Domain 생략을 사용하고 기존 Origin 검사/no-store를 유지한다. 로컬 HTTP는 Secure 속성을 환경에 맞게 분리해 검증한다.
3. 새 테이블 `session_extension_policies`의 PK는 `(session_id, extension)`로 두고 기존 정책 CHECK 제약을 유지한다. 세션과 기본 고정 7행을 한 D1 batch로 생성하고 성공 후 쿠키를 응답한다. 실패 시 절반만 초기화된 세션을 노출하지 않는다. D1 batch의 트랜잭션 동작은 [공식 문서](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)를 근거로 한다.
4. 모든 정책 SELECT/UPDATE/INSERT/DELETE와 커스텀 200개 상한의 count에 같은 session_id 조건을 붙인다. 고정 행 7개 불변식도 세션별로 검사한다. API 입력의 별도 session_id로 다른 세션을 선택할 수 없게 한다.
5. 업로드 요청도 같은 쿠키에서 서버가 세션을 확정하고, 기존 판정 시점 T에 **그 세션의 DB 정책**을 읽는다. 화면에서만 분리하거나 업로드에 전역 정책을 남기는 구현은 불완전하다. 서버 검증·전송/저장 성공 구분·수동 재시도는 유지한다.
6. 정책 변경·업로드에 쿠키가 없거나 만료됐으면 명시적 세션 오류로 중단한다. 변경/업로드 도중 조용히 빈 정책 세션을 만들거나 전역 정책으로 대체하지 않는다. UI에서 새 세션을 준비하고 정책을 재조회한 뒤 사용자가 다시 실행하도록 한다. 쿠키 차단 시에도 공유 정책으로 우회하지 않는다.

현재 전역 테이블의 사용자 변경값을 새 세션에 복사하지 않는다. 기존 migration은 보존하고 후속 migration으로 새 테이블을 추가한다. 현재 전역 테이블은 전환 후 제품 API에서 사용하지 않으며 이번 검토에서 삭제하지 않는다. 외부 인증/Redis/KV/ORM 도입은 필요하지 않다.

## 시작·유지·만료의 의미

- **처음 발급된 세션**: 고정 7개 unchecked, 커스텀 0개.
- **같은 세션 새로고침**: DB의 변경 상태 유지. 과제의 새로고침 유지 요구와 일치한다.
- **같은 브라우저의 새 탭**: 쿠키를 공유하므로 같은 정책. 별도 브라우저/프로필 등 독립 쿠키 저장소는 새 정책.
- **브라우저 종료**: 세션 쿠키도 브라우저 복원 기능으로 살아날 수 있어 종료를 확실한 초기화 경계로 삼지 않는다. 세션 쿠키에는 Expires/Max-Age를 두지 않는 안을 기본으로 검토하되 서버 만료를 별도로 둔다.
- **만료**: 생성 후 고정 24시간을 AI의 초안으로 제안한다. 확정된 요구값이 아니다. 서버가 expires_at으로 유효성을 검사하며 만료 후 새 세션은 초기 상태다. 새 세션 생성과 정책 삭제를 구분한다.
- **확실히 새로 시작**: 시연 재시작이 필요하면 명시적 ‘새 데모 시작’ 동작으로 새 세션을 발급하는 방안을 추가 제안한다. 쿠키 교체는 같은 브라우저의 다른 탭에도 영향을 준다는 안내가 필요하다. 아직 승인된 UI 기능이 아니다.

## 공유 자원과 정리

- 기존 `upload_budget`의 앱 전체 누적 상한은 유지하는 안이다. 세션을 새로 만들어 저장 예산을 초기화하거나 늘릴 수 없어야 한다. 정책은 독립되어도 전체 예산 소진·서버 자원 사용은 다른 세션에 영향을 줄 수 있다.
- R2는 비공개 UUID 저장 경로를 유지할 수 있다. 이번 정책 격리만을 위해 세션별 버킷이나 파일 조회/삭제 API를 추가할 필요는 없다. 세션 만료가 파일 삭제·누적 예약 환급을 뜻하지 않는다.
- DB에 세션마다 7~207행이 생긴다. expires_at 인덱스·정책의 세션 FK/삭제 규칙과 소량 단위 정리가 필요하다. 초기 구현은 세션 생성 시 제한된 수의 만료 행만 정리하는 안을 검토한다. 주기 스케줄·크론은 이번에 만들지 않는다. 접근이 없어도 물리 삭제까지 끝내야 하는 운영 요구가 있다면 별도 정리 작업을 합의해야 한다.
- 익명 세션 발급은 봇/반복 생성에 의한 DB 사용을 자동으로 막지 않는다. 기본 발급 수 상한과 만료 정리의 한도를 구현 계획에서 정해야 하며 무료 비용이나 완전한 사용자 격리를 보장하지 않는다. IP 주소를 사용자 식별자로 대신 사용하지 않는다.

## 구현한다면 필요한 로컬 TDD 검증

| 대상 | 확인할 동작 |
| --- | --- |
| 최초·재접속 | 새 A/B 각각 고정7개 unchecked·custom0, A 수정 후 같은 세션 새로고침 유지 |
| 조회·수정 격리 | A의 fixed/custom CRUD가 B에 영향 없음. 같은 확장자를 A/B가 각자 등록 가능 |
| 상한·경쟁 | 세션별 custom200개, 같은 세션 중복/경쟁 원자성, 다른 세션 상한 분리 |
| 실제 업로드 | A는 exe 차단·B는 허용일 때 실제 로컬 R2 미저장/저장. 각 요청이 자기 세션 T 정책 적용 |
| 초기화 실패·병행 | 세션/고정7행 batch 원자성, bootstrap 완료 전 정책/업로드 잠금, 첫 접속 병행과 쿠키 거부 시 동작 |
| 쿠키·만료 | 위조/누락/만료 토큰으로 다른 세션에 접근 불가. 업로드 도중 만료 경계의 명시적 실패, 조용한 허용 없음 |
| 브라우저 경계 | 별도 Playwright context 간 격리, 같은 context의 탭은 공유. 탭 방식 선택 시 opener/탭 복사도 별도 검증 |
| 기존 회귀 | 저장 응답 불확실·수동 재시도·전송100%/저장성공·T 전후 정책 변경·전체 예산 불변식 유지 |

위 표는 검토 당시의 후보다. 이후 선택한 최소 범위의 실제 구현·검증은 TDD_PLAN/TDD_LOG/VALIDATION의 SESSION-01을 따른다. 만료 등 채택하지 않은 후보를 구현·통과로 표시하지 않는다. 원격 리소스는 변경하지 않으며 배포는 이후 사용자의 명시적 요청 시에만 수행한다.
